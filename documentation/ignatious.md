# Ignatious API

The running application's `/docs` and `/openapi.json` endpoints are the authoritative API reference. All routes use the `/api` prefix. There is no authentication; see [SECURITY.md](../SECURITY.md) for deployment restrictions.

## Resources

| Resource | Routes |
| --- | --- |
| Tasks | `GET/POST /api/tasks/`, `GET/PATCH/DELETE /api/tasks/{id}` |
| Hierarchy | `GET /api/tasks/{id}/ancestors` |
| Scheduling | `POST /api/tasks/assign-sprint` |
| Sprints | `GET/POST /api/sprints/`, `PATCH/DELETE /api/sprints/{id}` |
| Epics | `GET/POST /api/epics/`, `GET/PATCH/DELETE /api/epics/{id}` |
| Assignees | `GET /api/users/`, `POST /api/users/add/`, `PUT/DELETE /api/users/{id}/` |
| Status labels | `GET /api/statuses/` |
| Needed work | `GET /api/needed-tasks/`, `POST /api/tasks/{id}/needed-tasks`, `PATCH /api/needed-tasks/{id}` |
| Materialization | `POST /api/needed-tasks/{id}/materialize` |

## Tasks and Planning

New tasks default to `Backlog` and project 1. Valid status labels are `Backlog`, `Ready for Action`, `In Progress`, `In Review`, and `Complete`.

```json
{
  "title": "Prepare a release",
  "description": "Verify the fresh-clone setup",
  "status": "Ready for Action",
  "project_id": 1
}
```

Task-list filters include `status`, `epic_id`, `project_id`, `sprint_id`, `parent_id`, `roots_only`, `unscheduled`, `resolution_state`, and `needs_attention`. Do not combine `roots_only` with `parent_id`, or `unscheduled` with `sprint_id`.

Sprints use a `YYYY-MM` month and are unique per project/month. Children inherit their parent's sprint. Use branch assignment to move root tasks and all descendants atomically. A task cannot be moved beneath itself or a descendant. Nonempty sprints and tasks with children cannot be deleted.

Pass the task's last-read `revision` as `expected_revision` in a PATCH request to reject stale updates with HTTP 409. Omitted fields remain unchanged; explicit `null` clears nullable fields.

```json
{
  "status": "In Progress",
  "expected_revision": 1,
  "description": null
}
```

Resolution states are `Unresolved`, `Partially resolved`, `Resolved`, and `Deferred`. Any state other than `Unresolved` requires an explanation in `resolution`. Task status, resolution, and review notes are independent.

## Needed Work

Needed items have a kind (`Decision`, `Investigation`, or `Action`) and state (`Open`, `Linked`, `Resolved`, or `Dismissed`). Use `open_only=true` to list Open and Linked items across nesting levels.

A stable `source_key` makes creation retry-safe within a task; reusing it with different content returns HTTP 409. Materializing a needed item creates a subtask or links existing same-project work. Repeating materialization returns the existing link. Completing linked work does not resolve the needed item; resolving or dismissing requires an outcome in `resolution`.

Needed-item updates also accept `expected_revision`. Task deletion is refused when needed-item records reference the task, preserving the audit trail.

## Errors and MCP

Common responses are 400 for incompatible hierarchy/filter choices, 404 for missing resources, 409 for conflicts, and 422 for invalid input. Do not assume every creation route returns 201; consult the generated API schema.

The supported MCP implementation and setup instructions are in [MCP/README.md](../MCP/README.md). Tool schemas are generated by the official SDK from the Python adapter rather than maintained separately in JSON.
